# Deploy — 3 September 2026

Two Workers ship independently. The website fix is the console; the brain fix
is the app. Run them in this order (site first: it is the thing a stranger
sees, and it does not depend on the app deploy).

## 1. The website — num-console

Puts the real home page back at itsnum.com/ and the ads landing page at
itsnum.com/ask/. Right now production still has the ads page as the home page
and /ask/ 404s.

    npx wrangler deploy --config wrangler.jsonc

Then check, in this order:

    curl -s https://itsnum.com/ | grep -o '<title>[^<]*</title>'
    # expect: NUM — Your AI travel concierge, in 38 countries
    curl -s -o /dev/null -w '%{http_code}\n' https://itsnum.com/ask/
    # expect: 200

**Point the ads at `https://itsnum.com/ask/`** — Meta and Reddit both. Until
that is changed, paid traffic lands on the home page, which is the right front
door for the site and the wrong one for a campaign that bids on a first
message.

## 2. The app — num-app

    npm run release:ship

The release script runs the suite (2566 tests) before it bumps the version, and
refuses to deploy a stale stage. **Do not pass `--force`.**

Then:

    curl -s https://app.itsnum.com/api/version | head -c 200
    # expect the new version, and connected.whatsapp: false until step 3

## 3. WhatsApp — when the sender exists

The code has been ready and tested for days; it is dark by configuration, which
is deliberate — a half-configured door stays shut. Two things turn it on, and
neither is a code change:

    npx wrangler secret put WHATSAPP_ENABLED        # value: true
    npx wrangler secret put TWILIO_WHATSAPP_FROM    # value: whatsapp:+1XXXXXXXXXX

`TWILIO_WHATSAPP_FROM` must be a sender **approved for WhatsApp in Twilio** —
either a real WhatsApp Business sender (Meta business verification, a number
that is not already on a personal WhatsApp account) or the Twilio sandbox
number while testing. Twilio's webhook for that sender points at:

    https://app.itsnum.com/api/whatsapp/inbound

The landing page's "Message Num on WhatsApp" button no longer has a number
typed into it. It asks `app.itsnum.com/api/version` for `whatsapp_number`,
which the Worker publishes only when both settings above are present and valid.
So the moment the secrets are set the button appears by itself — no second site
deploy — and it can never appear before there is somebody to answer it.

## 4. Reddit Pixel — after the console deploy

The pixel ships with the site deploy in step 1. Once it is live:

   `https://itsnum.com/ask/` and confirm a **PageVisit** appears.
2. Ads Manager → **Set up events** → make **Lead** the conversion event, and set
   the campaign objective to optimise for it. Do NOT leave the campaign
   optimising for clicks or PageVisit: that buys people who load a page, which
   is the cheapest and least valuable human on the internet.
3. The other two events report themselves once traffic arrives — **ViewContent**
   (Num answered twice) and **SignUp** (added to the home screen).

Pixel `a2_jgfeykixrdo7`, on 78 pages — every page that already carried the Meta

## 5. URGENT — where the Reddit ads actually point

The live campaign (`global-pretrip-film1`) lands on **`app.itsnum.com/install/`**, not on
itsnum.com. 2,305 of the 3,479 visitors NUM has ever had arrived there. That page had **no ad
pixel of any kind, on either network** — so every one of those clicks was invisible to the
system deciding who sees the ad next.

Fixed in this deploy: the Reddit pixel is now on `app-public/install/index.html` and on the app
shell, and `num-track.js` reports `first_message_sent` to Reddit as **Lead** from both. That
means the campaign starts learning the moment the app deploys, without waiting for the campaign
URL to change.

Also: `itsnum.com/install` (same path, wrong host) has never existed and answers 404. Any ad,
post or printed link that drops the `app.` subdomain lands a paid click on a dead page.
`public/_redirects` now sends `/install` and `/install/` to `/ask/`.

Still worth doing, in Ads Manager: point the campaign at **`https://itsnum.com/ask/`**, which is
the page with the concierge box on it. `/install/` asks for an install before Num has said a word
— that is the funnel this week's numbers indict.

## What changed in this deploy

- **The brain "outage" was a label.** Both corrective retries in /api/num
  rebuilt the result object and dropped `_brain`, so healthy answers recorded
  themselves as lane `<tier>:none`, brain NULL, and priced at `undefined`. 12
  of the 30 real asks in the last three days looked like that; every one of
  them was `quality: retried`, and every one of them shipped a good answer.
  Fixed in `worker/routinglabel.mjs`, with the retry now attributed to the
  model that produced the text that shipped.
- **A turn that recovers on the retry stops being degraded.** The uptime probe
  pages on `degraded: true`; a corrective retry only returns when Claude
  answered, so carrying the old flag forward would page for an outage that had
  already resolved in front of the guest.
- **/api/health now reads the signatures, not the mood.** A new `attribution`
  check warns when a fifth of a day's answers arrive with nobody's name on
  them. Warning, never a page — it needs a human eventually, not this minute.
- **The MCP integrity monitor stopped asking as a guest.** `concierge_answer`
  runs the full guest pipeline, so the monitor's one question was landing in
  num_asks as a traveller's. It now sends `X-Num-Probe: 1` and the MCP surface
  forwards it. Real partner traffic still counts.
- **Cost attribution.** `askNum` reports the model it actually used, including
  the strong-model escalation, so an Opus rescue no longer prices as Haiku.
- **Haiku had no price.** Every bulk-lane answer was charged at Opus's rate
  ($0.056 vs $0.061), so the router's whole saving was invisible in the only
  ledger that judges it. Priced properly now.
- **Reddit Pixel installed** on 78 pages with a conversion layer that reports
  the first message as a Lead. See step 4 above.
