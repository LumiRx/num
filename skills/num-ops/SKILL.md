# NUM operations

Every rule here exists because it already went wrong. The dates are real. If a
rule seems paranoid, read the incident next to it — that's the cost of skipping it.

## Start here: load the rules that already exist

`AGENTS.md` lives at the root of the app worktree and is the canonical
convention file. **Read it before acting** — it is not auto-loaded in Cowork, so
it is invisible unless you go get it.

```
~/num-worktrees/app-main/AGENTS.md
```

This was the failure of 2026-08-04: `AGENTS.md` already said *"`main` and
`backend-fastapi` share this remote but have no common ancestor. A force-push
across them deletes a codebase."* Nobody read it, and a session spent an hour
walking toward exactly that push. The knowledge existed; the loading did not.

Read it first. The rest of this skill covers what AGENTS.md does not: the
environment traps specific to running as an agent in this repo.

## Then run the preflight — one command, all the checks

```bash
bash scripts/preflight.sh              # bundled here, also at app-main/scripts/
bash scripts/preflight.sh --no-fetch   # skip the network hop
```

It reports branch tracking, lineage relative to `origin/main`, uncommitted
work, stale lock files, and whether the live surfaces actually answer. It is
read-only by construction — no git writes, so it cannot create the lock files
described in §1.

Two things it will shout about, both of which caused real incidents:
`NAME MISMATCH` (the branch doesn't track its own name) and `NO COMMON
ANCESTOR` (you are about to cross lineages). If either appears, stop and read
the relevant section below before running anything else.

If it reports **GIT IS NOT READABLE FROM HERE**, treat every git-derived line
as unknown rather than clean — that message exists because the first version of
the script silently printed "uncommitted paths: 0" for a repo it could not read.

## 1. Never run git *writes* from the Cowork sandbox

Read freely — `git log`, `git status`, `git show`, `git config`, `git rev-list`
are all fine and cheap. But **do not run `commit`, `add`, `reset`, `rebase`,
`merge`, or `worktree add`** from the sandbox in this repo.

Why: the sandbox writes through a mount that cannot delete files it created. A
failed git write leaves a `HEAD.lock` or `index.lock` owned by the sandbox uid,
and **the sandbox cannot remove it**. The next command — yours or the user's —
fails on that lock. Each retry creates the next obstacle.

On 2026-08-04 this cost five round trips: `index.lock`, then `HEAD.lock`, then
`index.lock` again, each one generated by the attempt to clean up the last.

**The working pattern:** write files with the file tools, run tests, then hand
the user a commit command. They own the directory, so `rm -f .git/*.lock` works
for them even when the lock belongs to the sandbox.

Pushing is not possible from the sandbox at all — no SSH credentials. Don't
plan around it.

## 2. Branch names in this repo lie — verify tracking before you act

Before any `push`, `reset`, `rebase`, or `merge`, run:

```bash
git config --get branch.<name>.remote
git config --get branch.<name>.merge
```

The branch called **`main`** in `~/Documents/Claude/Projects/NUM` tracks
`refs/heads/backend-fastapi`. It shares **no ancestry** with the real
`origin/main`. `git push origin main` from there was asking to replace the
entire Worker lineage with the Python backend; git rejected it twice as
non-fast-forward, and a `--force` would have destroyed ~89 commits.

A second cheap check that would have caught it:

```bash
git merge-base --is-ancestor <local-branch> origin/main && echo "same lineage" || echo "DIFFERENT LINEAGE — stop"
```

Run it before proposing any push. It costs one command and it is the difference
between a normal day and a restore-from-backup day.

## 3. Fetch before you build on a base

`git log` shows you a local branch. It tells you nothing about whether the
remote moved. On 2026-08-04 a commit was built onto a `main` that was 89
commits behind, discovered only when the push was rejected.

```bash
git fetch origin
git rev-list --left-right --count origin/<branch>...<branch>   # left=remote-only right=local-only
```

If the sandbox cannot reach GitHub (it usually cannot — no credentials), say so
out loud *before* committing rather than after the push fails. "I can't verify
the base is current" is useful information; silently assuming it is, is not.

## 5. Deploys: the right config, then verify it took

Three Workers share one D1 database (`num-db`,
`823979c8-b118-4a8a-953a-e07655205cf5`). They deploy differently, and using the
wrong invocation silently deploys the wrong thing:

- **num-app** — `npx wrangler deploy --config wrangler.app.jsonc`, but prefer
  the staged path: `npm run release:stage` (gated on `npm test`) →
  `node scripts/release.mjs ship`.
- **num-console** — **bare** `npx wrangler deploy` (root `wrangler.jsonc`). It
  owns `itsnum.com/*`. When its routes lapse, traffic falls through to DNS and
  the retired `itsnum.pages.dev` Pages project, which 301s back to the apex —
  an infinite redirect loop. That was the 4 Aug outage.
- **num-growth** — separate Worker, separate config.

**Always verify after shipping.** A deploy that reports success and a product
that works are different claims:

```bash
curl -s https://app.itsnum.com/api/version    # expect the version you just shipped
curl -s https://app.itsnum.com/api/health     # expect {"verdict":"ok"}
curl -s -o /dev/null -w "%{http_code}\n" https://itsnum.com/
```

## 6. Monitoring: what can and cannot see what

These are physical constraints, not preferences. Re-deriving them costs a
deploy cycle each time.

- **A Worker cannot fetch its own public hostname.** The subrequest loops back
  and Cloudflare answers **HTTP 522**. `num-app` probing `app.itsnum.com`
  produced a false outage while the app was healthy. Crying wolf is worse than
  a blind spot, because people mute wolves.
- **Same-zone subrequests succeed from cron and fail from a request handler.**
  This made `/api/health` report *down* while the cron reported *ok* — a
  monitor disagreeing with itself. The endpoint now reports the last cron
  verdict (`runHealthFromLastRun`) rather than re-probing.
- **The app host is covered from outside**, by `.github/workflows/uptime.yml` +
  `scripts/uptime.mjs` on GitHub's runners. GitHub only runs `schedule:` from
  the **default branch**, so that file lives on `origin/main` regardless of
  which lineage the code under test belongs to.
- Never follow redirects in a probe. `redirect: 'manual'` is what turns a loop
  into an immediate failure instead of a slow success.

## 7. Write guard tests that actually guard

A test that passes on broken code is worse than no test — it converts an
unknown risk into false confidence.

**Before trusting any guard test, break the thing it guards and watch it fail.**

```bash
cp file.mjs /tmp/f.bak
sed -i "s/<the correct thing>/<the broken thing>/" file.mjs
node --test file.test.mjs        # MUST fail here
cp /tmp/f.bak file.mjs
node --test file.test.mjs        # and pass again here
```

Two guards written on 2026-08-04 passed against deliberately broken code:

- `TARGETS.some(t => t.url.includes('app.itsnum.com'))` — passed while the probe
  was repointed at the wrong host, because a *sibling* target still matched.
  Assert per-item, not with `.some()` across a collection.
- `assert.match(wf, /schedule:/)` — passed on `xschedule:`, the exact typo that
  disables the monitor. Anchor patterns: `/^\s{2}schedule:$/m`.

Both were found only by running the mutation. Neither was found by reading.

---

## 8. Don't couple the test suite to the network

`release:stage` is gated on `npm test`. A network assertion in that suite means
**an outage blocks shipping the fix for that outage**. Keep probe *judgement*
pure and testable offline; let CI exercise the live path separately.

---

## 9. Before claiming environment state, go look

The through-line in every incident above: an assumption that was one cheap
command away from being checked. A branch name, a base's freshness, whether a
file exists, whether a deploy took, whether a test really fails on bad input.

Prefer the command over the recollection. When you can't check — no
credentials, no access — say that plainly instead of presenting the assumption
as a finding. "I can't verify X from here" is a useful sentence and costs
nothing.

## Recovering from a stuck lock

```bash
cd <the worktree>
ls -l .git/*.lock              # 0 bytes = stale, from a crashed process
rm -f .git/*.lock              # the user can do this; the sandbox cannot
git status                     # confirm state before the next write
```

If the lock is owned by the sandbox user, that confirms rule 1 was broken. Hand
the command to the user and stop issuing git writes.
