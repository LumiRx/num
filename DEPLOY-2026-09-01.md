## Order matters in exactly one place

`growth/worker.js` gained `/api/host/profile`, which does a bare
`SELECT services_json, pricing_json, charge_mode, calendar_token …
FROM num_hosts`.

**Production's `num_hosts` has none of those columns.** Migration 0013 has
never been applied. Deploy growth before the migration and that endpoint
returns a 500 on every call.

Blast radius today is zero — there are 0 hosts and the endpoint is behind
`hostAuth` — but it costs nothing to do it in the right order.

*(Checked the rest too: 0002 is unnecessary — `passengers.mjs` creates
`num_passengers` lazily. 0004's three tables are referenced by no code at all;
it is a spec for something never built. 0013 is the only one that matters.)*

## 1 · Migration first

```
cd ~/num-worktrees/app-main
npx wrangler d1 execute num-db --remote --file ./worker/migrations/0013_host_profile.sql
```

Twelve `ALTER TABLE` and one index. Safe as a single file run **this time**,
because none of the columns exist yet. If you ever re-run it, do it one
statement at a time — SQLite has no `ADD COLUMN IF NOT EXISTS`, and one
duplicate inside a transaction rolls back the whole thing.

Check:
```
npx wrangler d1 execute num-db --remote --command "SELECT COUNT(*) AS cols FROM pragma_table_info('num_hosts')"
```
Expect **28** (17 today + 11 new).

## 2 · Stage the app worker

```
npm run release:stage "chain booking engines, commission attribution, affiliate wrap, verified-number lockout fix"
```

This runs the tests again, builds, bumps to **0.8.230**, writes the changelog,
and uploads the version **without moving any traffic**. It prints a preview URL.

Open the preview URL and click around before step 3.

> **Why the release script and not `wrangler deploy`:** production currently
> reports `"version":"unknown"` on `/api/version`. That is the signature of a
> plain `wrangler deploy`, which does not pass `--var NUM_VERSION`. It means we
> cannot presently prove what code is live. Going through `stage`/`ship`
> restores that, and `ship` verifies the running Worker three polls in a row
> before it calls the deploy good.

## 3 · Ship it

```
npm run release:ship
```

Flips 100% of traffic, polls `/api/version` until three consecutive reads
agree, then runs the MCP integrity check against the live server. If anything
disagrees: `node scripts/release.mjs rollback`.

If you want to be cautious: `node scripts/release.mjs ship 10` puts one in ten
users on it first.
